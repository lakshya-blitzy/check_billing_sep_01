# Performance check: hello-world HTTP server

I measured this repository's hello-world HTTP server (`server.js`, whose handler answers every request that reaches it with a fixed `Hello, World!\n` body on hardcoded port 3000, while Node's own HTTP parser below it rejects what it cannot parse — an unrecognised method token, a missing `Host` on HTTP/1.1, a malformed request line, oversized headers — with `400 Bad Request` or `431 Request Header Fields Too Large` before the handler runs, and closes a `CONNECT` unanswered) from the outside, driving it over TCP from a separate client process at `127.0.0.1:3000`: 200 requests at each of two concurrency levels, dispatched in `Promise.all` waves of the level's width and timed with `process.hrtime.bigint()`. Every measurement below is quoted verbatim from that one run's console output; the only figures it did not print are derived from those printed values — the concurrency-50 wave count and mean wave makespan, and the throughput ratio between the two levels — and each shows its arithmetic where it appears. Nothing here comes from any other run, harness or baseline.

At concurrency 1, where the 200 requests are strictly serial, the batch took elapsed 34.095372ms at amortized_latency 0.17047685999999998ms and throughput 5865.89875012949req/s. Because no two requests overlap at this level, that amortized_latency is a genuine mean per-request latency.

At concurrency 50 the batch took elapsed 24.440176ms at amortized_latency 0.12220088000000001ms and throughput 8183.247125552614req/s. That amortized_latency is not a per-request latency here but the reciprocal of throughput, i.e. mean amortized service time; this run produced no per-request latency statistic at this level and none is inferred. What can be said about the waves is the mean wave makespan, derived as 24.440176ms / 4 waves (200 requests / 50 per wave) = 6.110044ms, which each wave's slowest request sets and which is therefore an upper bound on the typical request rather than a measurement of it.

The throughput ratio between the two levels, derived as 8183.247125552614 / 5865.89875012949 = 1.3950542745682355, is where the two levels compare directly. So raising the number of in-flight requests fiftyfold bought just under two-fifths more throughput: a real gain, but so far short of proportional that in-flight width cannot be what principally sets the achieved rate. This run does not localise what does set it, and the numbers cannot be read as the server saturating, because they are a lower bound on its capacity rather than its ceiling; the sub-linearity is equally consistent with the server being the limiter and with the measuring client being it.

Memory, for the measuring script's own process and not the server's: at idle, before any request, rss 46538752, heapTotal 5611520, heapUsed 4442392, external 1690124, arrayBuffers 10767 bytes; after the load batch, rss 57135104, heapTotal 10067968, heapUsed 6339392, external 1704739, arrayBuffers 24206 bytes. The server's memory was not measured at all, since `process.memoryUsage()` reports only the process that calls it.

Limits worth holding in mind while reading the above:
- First-request JIT warm-up may inflate the slowest sample, which lands in the serial batch and raises its mean, so read the serial figure as slightly pessimistic; it is reported, not discarded.
- A co-resident client competes with the server for CPU, both being single-threaded Node processes on the same host, so no throughput figure is attributable to the server alone.
- Keep-alive socket reuse shapes the achieved concurrency: the default agent keeps connections alive, so only the first wave pays TCP handshake cost and later waves reuse warm sockets.
- The `Promise.all` wave barrier gates each wave on its slowest request, which makes the throughput figures a lower bound on what the server can sustain rather than its ceiling.
- This is a single, unrepeated run, with no trial-to-trial variance characterised and no percentile computed, so no figure here should be treated as a stable value.
- The memory figures are the script's process; the server's own memory is not measured.

Suggestions for future investigation, not findings: per-request percentiles, a wider concurrency sweep, repeated trials, server-side instrumentation, and CPU or GC data.
